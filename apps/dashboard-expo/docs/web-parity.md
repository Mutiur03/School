Updated with each port batch. Endpoints are the ones the web page calls today (all exist on
`main`); the Expo app talks to the same endpoints with the same tenant/session rules.

Status: **done** = same features as the web page · **partial** = usable, gaps listed ·
**missing** = still the "not built yet" placeholder (or no screen).

Cross-cutting notes:

- **Form controls**: desktop web keeps the web's input look (40px, 14px text). On native and
  phone-width web the controls are designed for touch instead of mirrored: 48px fields, 16px
  text, Next/Done chaining, keyboard-aware scrolling, bottom-sheet pickers and phone mark entry
  (README → Form controls).

- **Native build (batch 7)**: `expo-document-picker` and `expo-image-picker` power every upload
  on native through one `FilePicker` / `PickFilesButton` (`src/lib/files/pick-file.ts`; images
  only → photo library, otherwise the document picker; bytes go up as a Blob). The web keeps a
  hidden `<input type="file">`. Date fields use `@react-native-community/datetimepicker` on
  native (Android dialog, iOS bottom sheet with the inline calendar) and `<input type="date">` on web. This changed
  the runtime fingerprint, so it needs the new APK.
- **Excel import**: the web parses .xlsx in the browser with SheetJS 0.18.5 (open advisories)
  for students and subjects only; the server has no file-import endpoint. The app reads .xlsx on
  the device with a small reader on `fflate` (`src/lib/files/xlsx.ts`: first sheet, shared /
  inline strings, date cells → YYYY-MM-DD; 5 MB, 10,000 rows and a 60 MB unzip budget), checked
  against SheetJS on the web's own template, then applies the web's rules
  (`src/features/import/models.ts`) and posts to the existing bulk endpoints. Teachers and marks
  have no Excel import on the web, so none here.
- **Stored files** resolve against `EXPO_PUBLIC_CDN_URL` (staging: `https://cdn.lbphs.gov.bd`,
  the deployed web dashboard's `VITE_CDN_URL`). Checked (batch 8): this is the platform-wide
  public domain of the one R2 bucket, not a per-school custom domain. Every dashboard build in
  `deploy-pages.yml` (LBP, admin, teacher, student and the cross-tenant super admin) gets the
  same `secrets.LBP_VITE_CDN_URL`; `client-next` uses one `NEXT_PUBLIC_CDN_URL` for every tenant
  site; the server serves `env.R2_PUBLIC_URL` and isolates tenants by key prefix
  (`tenantR2Key` → `${schoolId}/…`, `assertTenantR2Key`); `schools` has no CDN/storage column.
  So one build-time base is correct for every tenant, as on the web.
- **Column-header sort** (batch 8): `DataTable` columns with a `sortKey` get a sort header
  (asc → desc → off) on wide screens, on every web page that has header sort menus; phones keep
  the cards (and the Sort select where the web has one). Header filter menus map to the
  toolbar filters.
- **Excel export** (batch 6 decision): the web builds .xlsx in the browser only for the five
  account reports. SheetJS from npm (0.18.5) has open advisories (prototype pollution, ReDoS)
  and exceljs is barely maintained and pulls Node-only deps, so the app writes **CSV** with
  no library (`src/lib/files/csv.ts`: UTF-8 BOM, quoted cells, formula-injection guard,
  amounts from paisa). Admissions and registrations use the server-built xlsx/zip exports.
  Fees collect/receipts/reports and vouchers have no export on the web either.
- **Super admin (platform mode)**: no link on the school-code screen. The server's platform access
  code (`PLATFORM_ACCESS_CODE`), typed or scanned like a school code (`{ target: 'platform' }` from
  the lookup), opens an email + password login (POST /api/auth/super_admin/sessions) against the
  build's `EXPO_PUBLIC_DIRECTORY_URL` (staging: `https://superadmin.mutiurrahman.com`), never a host from the lookup. The web overview and the
  app's user menu show the code as a QR. Without the server feature it is a plain "code not
  found". The code opens sign-in only and grants nothing, and a school code can never
  pre-select super_admin. Platform mode is its own tenant: key `_platform.<host>` (no hostname
  contains `_`), its own SecureStore slot, API client, session and query namespace, so platform
  and school data never share a cache. The stored choice is honoured only while it matches the
  build's super-admin origin; Logout and "Use a school code instead" forget it. Only super_admin
  sessions are kept from that login, a school role is signed out of platform mode and a
  super_admin is signed out of a school (the server enforces the same: `authenticate(['super_admin'])`
  plus the super-admin host check on every request). Every tenant-affecting action goes
  through one confirm dialog with a synchronous double-submit guard.

### Admin authz / tenant gaps seen in batch 4 endpoints (not fixed here; backend unchanged)

- **SMS settings read** (`GET /api/sms-settings`): returns the whole settings row to school
  admins, including the encrypted `api_key` and the other provider credential columns. The app
  parses only the template/toggle fields and never displays or stores the rest.
- **SMS settings write** (`PATCH /api/sms-settings`): strips only `api_key`, `api_url`,
  `sender_id`, `service_type` and `sms_balance`, then passes every remaining body key to
  `prisma.update` (mass assignment: e.g. `school_id` or `id` would be accepted). The app sends a
  fixed whitelist (`settingsPatchBody`, covered by tests).
- **Head message** (`POST /api/teachers/head-message`): `teacherId` is not checked to belong to
  this school (FK checks bypass RLS) and `headRole` is not validated against the two roles. The
  read/update paths fall back to an unscoped `findFirst` and a `global` cache key when no school
  id is resolved.
- **Bulk SMS / student count** (`/api/sms/bulk-sms`, `/student-count`): `classNames` gets little
  validation; a bad input surfaces as a 500 (`throw new Error`) instead of a 400.
- **Student TC / reactivate / testimonial** (`/api/students/:id/tc|reactivate|testimonials`):
  tenant isolation relies on RLS around `findUnique({ id })`, with no explicit school check.
- **Teacher password rotation** emails the new credentials to the head teacher as a side effect;
  the confirmation in the app says so.
- `GET /api/staffs` and `GET /api/teachers` are optional-auth (public profile data for
  non-admins), by design.

### Money handling (batch 5)

The server stores amounts as `Decimal(12,2)` and sends them as JSON numbers in taka; fee pricing
runs in integer paisa (`Math.round(x * 100)`), and the reports sum and round with
`Math.round(n * 100) / 100`. The app turns every amount into integer paisa where it parses the
response (`src/lib/money`), adds up only integers, parses typed amounts digit by digit (no float
maths), and turns paisa back into taka only when it builds a request body. Fee collection sends
just the installments (`fee_head_id` + `month`); the server works out the amounts.

### Admin authz / data gaps seen in batch 5 endpoints (not fixed here; backend unchanged)

All fee and accounts endpoints are admin-only and scoped by the school id from the session
(`@SchoolId`); the app never sends a `school_id`.

- **Vouchers** (`POST /api/vouchers`): there is no idempotency key or unique business key, so a
  request that times out and is sent again could post twice. The app sends one request per
  confirm, keeps the button disabled while it runs, and re-reads the list after a failure.
  Fee collection is protected in the database (one receipt item per student, year, fee and month).
- **Receipt numbers** are `max + 1` per school, so deleting the newest receipt reuses its number.
  Voucher numbers come from the row id.
- **Fee structure save** (`PUT /api/fee-structures`) deletes the class's rows and inserts them
  again, rather than updating them.
- **Account head parent**: the server rejects only a head that is its own parent. Longer cycles
  are accepted. The app lists heads that are in a cycle at the top level, so they stay visible.
- `accHeadFormSchema` (shared) does not limit opening balances to 2 decimals. The app's money
  input does.
- Server reports add up floats and round each result (a difference of at most a paisa is
  possible). The app shows the server's totals and adds up its own subtotals in paisa.
- `GET /api/fee-receipts` returns at most 500 rows, with no paging.

### Admin authz / data gaps seen in batch 6 endpoints (not fixed here; backend unchanged)

The app never sends a `school_id`; every screen relies on the server's session scoping.

- **Gallery upload** (`POST /api/gallery/upload`): trusts the client `status`, so a student
  uploader could mark their own photo approved. The app always sends `approved` only from the
  admin screens.
- **Gallery thumbnails** (`/setEventThumbnail/:eventId/:imageId`,
  `/setCategoryThumbnail/...`): no check that the event/category/image belong to the school
  (relies on RLS). The "events" category id is hard-coded `1`, and `category_id`/`event_id` on
  upload/update are not checked to belong to the school.
- **Citizen charter / syllabus**: reads fall back to `where: undefined` when no school id is
  resolved; the syllabus cache only clears the all/all key, so filtered reads can be stale (the
  app fetches all and filters on the client).
- **Class routine PDF**: no explicit school filter (RLS only).
- **Fee waiver update** (`PATCH /api/fee-waivers/:id`): does not re-check that the fee head is
  waivable (create does). The app only offers waivable heads.
- **Admission / registration forms**: `GET .../:id/pdf` is unauthenticated and `GET .../:id`
  is optional-auth, so anyone with an id can read an applicant's PII. Status/update routes are
  optional-auth with assertions in the handler.
- **Registration settings save**: the notice is set to null unless `notice_key` is sent again
  (the app always resends the current key). `/years` returns only the latest 3 years (the app
  offers the latest year minus five plus next year).

### Teacher scoping gaps seen in the endpoints (not fixed here; backend unchanged)

- **Students** (`GET /api/students`, `/api/students/attendance-overview`, `/:id/attendance`):
  admin + teacher with no class scoping. Teachers get every student of the year, including
  guardian phones and addresses.
- **Attendance** (`/api/attendance/*`: getAttendence, addAttendence, getStats, save-and-send,
  send-sms, sheet): router-level admin + teacher only. No check that the teacher is assigned to
  the class/section, that `records[].studentId` belong to the `level`/`section` sent, or that the
  date is today, so any teacher can write any student's attendance for any day and trigger SMS
  sends (spending school credits) for any class.
- **Marks entry** (`PUT /api/marks`): scoped by _class teacher_ (canAccessStudent on the
  student's current enrollment). A class teacher can write every subject of their section; a
  subject-only teacher can't enter marks at all. Not checked: marks against the subject's upper
  limits, that the subject belongs to the student's class/year/group, that the exam covers the
  class, or a lock once results are published. Rejected students come back as per-row errors
  inside a 200.
- **Marksheet status** (`GET /api/marksheets/exams/:id/status`): admin + teacher, no class
  scoping (counts only).
- **Levels**: the login/refresh payload only carries the current year's `levels`, while the
  server authorizes from all years in the DB. The app therefore offers only this year to
  teachers (narrower than the server, never wider). `/api/level/*` is admin-only, so the app
  can't list a teacher's past assignments.
- **Teacher photo/signature save** (`PUT /api/teachers/:id/image|signature`): own id is
  enforced, but the key is only checked to be in the school's prefix, not under
  `teachers/`/`signatures/` or freshly signed for this teacher. A teacher could point their
  photo at another school object, and replacing it later deletes that object from storage.
- **Change password** (`POST /api/teachers/change-password`): server only requires 8+
  characters (the uppercase/number/special rules are client-side), and it doesn't bump
  `tokenVersion`, so other sessions stay signed in, contrary to the web page's notice.
- `/api/exams/getExams` is public (no auth); harmless for this screen but worth knowing.
